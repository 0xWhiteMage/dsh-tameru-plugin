# Changelog

## 0.2.0: Tameru engine 1.10.0 (not released)

Replay-only. Every engine number below comes from the engine's own replay of recorded and generated tool outputs (`docs/RESULTS-1.10.0.md` in the engine repository: one sealed look on commit `99db5bd`, paired against engine 1.9.0). **This plugin's own measurements ([MEASURED-VS-STOCK.md](docs/MEASURED-VS-STOCK.md), [REPLAY-VS-STOCK.md](docs/REPLAY-VS-STOCK.md)) were NOT redone for 0.2.0**: they describe engine 1.9.0 on Harness 0.2.2-rc.1. No real model has run, so there is no claim about answer quality, the provider's cache behaviour or the bill, and none about cost.

What the engine reports for the DeepSeek plugin's call settings on its sealed split (94 cases in 62 source clusters; 95% intervals, cluster bootstrap): characters saved 76.9% with a generic question (+63.7 points over 1.9.0 [+52.1, +73.0]), 76.6% with a tool-call-shaped question (+17.0 [+8.5, +26.2]) and 86.6% with a task question (+21.7 [+12.9, +31.7]); evidence kept 100%, 99.5% and 100%; the engine falls back to the original on 13.8%, 13.8% and 2.1% of the cases. Java and .NET stack-trace chains are 84 to 89% saved with all evidence kept. The engine's confidence separates "all evidence kept" from "something lost" with AUROC 0.988 [0.969, 1.000] on the tool-call-shaped question. What this does to a whole chat's cost is **not** measured: `scripts/replay.ts` has not been re-run.

### Disclosures
- **Secret redaction is turned on.** Every call passes the engine's opt-in `redact_secrets`: credential-shaped text in an extract, and in the new "dropped" part of its header, becomes `[tameru:redacted]`. It is on because this plugin keeps no original outside the chat itself. **Limit: when the engine declines (fail-open) it returns the original text unredacted.** That is safe only because the plugin never acts on a decline: the original stays in the chat exactly as it was, so nothing new reaches the model, and redaction never changes the decision. Tests plant a secret in a kept line, in a dropped-locator position and in a text that fails open.
- **`tameru_read_original` gained a `grep` parameter** (with `literal`, `ignore_case`, `max_matches`): the model can ask for the matching lines of an original, with line numbers (50 by default, 200 at most), instead of reading it in windows. The pattern comes from the model, so a regular expression that can backtrack catastrophically (back-references, look-arounds, repeated groups that repeat or alternate, more than three unbounded repeats) is refused, patterns are limited to 120 characters, lines are matched up to 600 characters and the search stops after 1.5 s. It still reads only results Tameru shortened, in the model's own chat. The tool description now tells the agent to re-read an original when the header's dropped list may hold what it needs.
- **Worker protocol 2.** The worker takes its field list, ranges and closed enums from the engine's own `tameru.protocol` (unknown fields are still refused; `ccr`, `log_dir`, summary and model options do not exist in it). The `version` reply carries the engine version, protocol, result schema and preset ids. Version 1 requests still work; a version 2 host talking to a version 1 worker sends version 1 fields only. Error replies are fixed codes or an exception type name and never contain request text. The worker accepts `pin_patterns` only as `{"literal": ...}` (see "Engine problems found").

### Changed
- **The vendored engine is Tameru 1.10.0** (`404d132`, branch `release/1.10.0`), byte for byte, now including its package data `presets.json`. `scripts/check_vendored.py` compares every file of the engine's package (not only `*.py`), and a test checks that `presets.json` ships in the npm package and that the vendored tree is never line-ending converted.
- **Acceptance is the engine's `decide()`.** The request carries the policy (the engine's `DSH_POLICY`, with the strength menu's confidence floor 0.85, 0.7 or 0.55; at least 1 token saved; a sanitized input is never accepted); the reply carries the decision and one closed reason (`ok`, `fail_open`, `risk`, `lost_fingerprint`, `low_confidence`, `no_gain`, `sanitized`, `not_enough_tokens`). `shorten.ts` acts on `accept` only and counts the reasons (`/tameru` shows them). A node test fails if any host file holds a confidence, risk or fingerprint threshold other than the values passed to the worker. The one check that stays in the host is the Harness's own token meter on the message it would write, header included. A worker that speaks protocol 1 gets the old rule from `src/host/legacy-decision.ts`, with the same policy numbers.
- **The call is the engine's preset `dsh-tool-result@1`** (extract strategy, 25% minimum saving, no stored originals) plus `redact_secrets` and `anchor_errors`. `anchor_errors` is on for every size, because the engine now caps its own probes. Measured by this plugin's tests on one PC (Python 3.13): a 1.2 million character code-shaped text takes about 1.9 s per request with it and about 0.7 s without, 100 to 450,000 characters take 0.01 to 0.7 s, and a six-result pass over 20,000-character logs takes about 0.4 s including worker start, so the 4 s request deadline and the 6 s pass budget hold. On code-shaped input with an empty question it also turned declines into accepted extracts.
- **The question is built by the engine.** The host sends the pieces (the tool call, the assistant turn after it, the last and the first real user message; the Artifact Trail, compaction summaries and other non-user messages are never "the user") and the worker uses the engine's shared `build_query`. The tool name and its arguments come before any user text, so a 2000-character Chinese message cannot push them out (tested). The TypeScript `buildQuery` stays only as the fallback for a protocol 1 worker. One difference from 0.1.x: the "last user message" is now the latest in the whole chat, as in the engine, not the latest before the result.
- **A result is decided once.** The memory of declined results is keyed on the result (its place in the chat and its length), not on the question, so a later step with a different question never rewrites a result that was already shortened and never asks the engine again about one it declined. (The engine's `stable_key` is not part of the key: it hashes the question, so using it would ask again whenever the question changed.) Tests: zero second rewrites across three changed questions, and no engine request for a declined result.
- **The header of a shortened result names what was dropped** and ends in `ref=N`, the token the Hermes plugin's headers also end in: `[Tameru: shortened from 20,007 to 179 characters; dropped: 399 log lines (step); read the original with tameru_read_original ref=5]`. The engine's three largest dropped categories are shown with their first locator, cleaned with the same function as the Trail (no markup, no control characters, no brackets) and capped at 150 characters; the header grew by about 30 characters in the test sessions (a test bounds the average at 160). Headers written before 0.2.0 said `reference N` and are still recognised.
- `/tameru` shows the worker's protocol and result schema, and the engine's decision counts for the chat.

### Engine problems found (reported, not fixed here; the engine repository was not touched)
- `src/tameru/protocol.py` `regex_risk` (about lines 80 to 118) does not catch polynomial backtracking: `a*a*a*a*a*b` is accepted as a `pin_patterns` regex and `compress_context` then does not return within 15 s on a 3,000-line text, which would block a single-threaded worker. This plugin's worker accepts literal pins only.
- `src/tameru/compress_context.py` `_dropped_summary` (about line 4341): the `dropped` locators are read from the original text, so with `redact_secrets=True` a credential can still appear in a locator. The worker redacts them with the engine's `redact_secrets_in`.
- `scripts/sync_to_harness.py` (lines 88 and 99) copies `*.py` only, so `presets.json` is neither copied nor checked by the sync; `check_vendored.py` here does both checks.

## [Unreleased]

### Changed
- **0.1.2: the interface is rebuilt to one design shared with the Hermes plugin** (engine repository `docs/PLUGIN-UI.md`, reviewed by five design specialists over four rounds). A solid bar drawn like the Harness's own goal bar (the old one had no background, so the chat scrolled visibly under it and long text appeared to bleed into it): a Tameru star whose colour is its state, the name Tameru (ためる), one status phrase, a context ring with `55% full`, then a **strength menu (Off · Less · Normal · More)** that replaces the mode select and the pause button, a **results** launcher and a **pins** launcher; no chevron, no green, no "new" marker. Details open as a **floating card** with two tabs (Shortened, Pins): rows say **what was run** (the host reads each result's tool call and shows the start of its command or path, cleaned and bounded), sizes are whole K in aligned columns, and one **Keep** lock button per row keeps that output in full; kept outputs sit below a `Kept in full` divider. The viewer has one header (`AI sees | Original`, remembered for the session). Pins offer Undo for five seconds. Every error says what happened, that the chat is unchanged, and what to do. The vocabulary and the drawings are shared files with tests (English and Chinese, with a forbidden-words test that keeps cost and saving wording out). Two font sizes taken from the Harness's own setting; measured on a 600 px window: the bar is 36 px and one line, the card is flush with the bar, columns align, and nothing overflows even at an 18 px user font. Uses the Harness's own hover cards and icons where they exist, each checked to be a real component with a plain fallback, and a failing bar falls back to a plain name instead of taking the message box with it.
- Review fixes in the same release: focus moves into the card and Tab hands over in both directions; Esc closes the card only where the person is; a change of strength no longer snaps back for a poll; Enter during Chinese input no longer adds a half-typed pin; one live region.
- The development tool no longer has a DS Bot option.
- **0.1.1: pinned to DeepSeek Harness 0.2.2-rc.3.** The desktop app updated itself from rc.1 to rc.3 and the Harness skipped the plugin as incompatible (`engines.dsh` must equal the running version). Re-tested: the full suite (111 tests, including the real session log, token meter and event bus) passes on rc.3, the stock trigger and pruner constants are unchanged, and the bar loads in a throwaway rc.3 Harness with the same bundle list as the author's profile and DS Bot. The replay and per-output measurements were not re-run.

### Added
- **One compact bar** in the input dock (`conversation.input.dock`), closed to a single ~30 px line, opening to Results, Pins and Settings: gauge, cleanups with viewer, one Keep switch per row, pins and three named confidence choices, from a bundled React client (`lib/client.js`, about 42 KB, only the Harness's shared modules) over an authenticated route `POST /api/tameru` (state, hold, view, pin, unpin, settings) that reuses the `/tameru` command code. It reaches only chats that are open and validates every payload. Settings changed there are saved in `<Harness home>/tameru/settings.json`. Found by running the real Harness web client: guide entries need `title` and `description` as functions, a dock component receives what the slot's `inject(sessionId)` returns, and an undeclared service silently fails a plugin; each is now covered by a test.
- `scripts/dev_harness.py`: serves the installed Harness against a throwaway home with a stub model and this plugin installed, to try the interface in a browser without touching a real profile.
- **Pins** (`/tameru pin`, `pins`, `unpin`, `purge`): a `tameru:pins` section of the system prompt (not interpolated), five lines of 300 characters, credential-shaped text refused, saved atomically in `<Harness home>/tameru/pins.json`, per chat.
- **Artifact Trail**: after a finished compaction, one user-role notice (source kind `tameru`, form `notice`) of typed, capped, sanitised facts about the replaced messages, added to the pre-step decision only when the step is admitted, derived entirely from the log so a restart repeats nothing, merged forward through later compactions.
- The plugin now declares `systemPrompt` and `tools` as required services. Using a Harness service that is not declared makes Cordis fail the plugin silently; a test now mounts the plugin on the real services to catch that.
- **A way back and user control.** `tameru_read_original` (a model tool, a plain definition so nothing is imported from the Harness at run time) reads a shortened result's original in windows; `/tameru changes`, `view`, `keep`, `restore`, `unkeep`, `help`. A result's state (shortened, restored, kept) lives in its visible header because the Harness lets a `tool/result` replacement change only its content, so it survives restarts and forks. Keep and Restore write the same price-event-then-replacement pair as the pass, citing the original and the node they replace. Changes asked for mid-turn are queued for the next step boundary. A restore expires after 3 model replies counted from the restore itself. The read tool's own results are never shortened.
- **Shortening at step boundaries.** An `agent/pre-step` listener (never `prepend`) that, above 75% of the Harness's own compaction trigger (computed the way `dsh-compaction-basic` does), replaces large old tool results with the engine's query-aware extract. Results that are errors, spilled to a file, already cut, not text, unread by the model, or among the newest four are never touched. Applied only when the engine's confidence is at least 0.7 and the change frees at least 35% of what it makes the provider rewrite. Writes the same `compaction/prune` + replacing `tool/result` pair the Harness's pruner writes, after re-checking that nothing changed while the engine worked and that no compaction is open.
- Stands down for chats whose compaction another plugin has taken over (an own `compactIfNeeded`, `compactNow`, `compactRegion` or `summarize` on the backend object, or `auto: false`).
- `/tameru` reports what was shortened in the chat, or why nothing was.
- Settings: `shorten`, `activation`, `minConfidence`, `share`, `protectRecent`, `minResultChars`, `maxPerPass`.
- A chat remembers results the engine already declined, so the same output is not sent to the engine again at every later step.
- `docs/REPLAY-VS-STOCK.md`: 40 simulated whole sessions (160 runs: stock and three Tameru settings each) against the stock Harness, with the real session log, token meter, stock pruner, this plugin's pass and the engine. **Result: at the shipped settings Tameru is cost-neutral (it almost never acts); with the confidence gate lowered it acts and sessions cost about 3% more while holding about 0.7 more of 5 needed facts.** No setting tried was cheaper than stock. `scripts/replay.ts` reproduces it.
- `docs/MEASURED-VS-STOCK.md`: the first measurement against the stock pruner, with its limits (per output, not per session; no cost claim). `scripts/compare_stock.ts` reproduces it.
- Skeleton: the plugin loads in DeepSeek Harness, starts the Tameru engine as an isolated Python worker, and `/tameru` reports the plugin and engine versions. Nothing is shortened yet.
- The worker protocol (version 1): a fixed list of accepted fields, no disk, network or model options, UTF-8 over stdin and stdout, exits when stdin closes.
- Fail-open engine client: a slow, crashed or misbehaving worker leaves every original untouched and rests for five minutes after repeated failures before being tried again.
- Engine vendored from tameru-compaction-system commit `9f1f1c4` (Tameru 1.9.0), with a check that the copy is identical.

- Contract tests against the real Harness packages (Cordis and the managed subprocess service), extracted on demand by `scripts/extract_harness.py`. They found two defects, both fixed: cleanup must be registered with `ctx.effect` (there is no `dispose` event), and a write to an already-ended worker must not raise an unhandled pipe error, which would stop the whole Harness.
- Verified in the real Harness (0.2.2-rc.1) with an isolated throwaway home and a stub model, never your own profile: the packed plugin installs; the Harness composes it with exactly one added row and nothing else different from stock; `/tameru` appears in the command list, runs, and is logged in the session; with `pythonPath` set it reports "Engine 1.9.0 (matches source commit 9f1f1c4), Python 3.12.14"; the worker runs as `python -I -B -P .../vendor/run_worker.py`; stopping the Harness leaves no worker behind.
- The package no longer ships Python bytecode (it would have shipped 16 `.pyc` files).
- A "loaded" line is logged through the Harness logger at startup.
